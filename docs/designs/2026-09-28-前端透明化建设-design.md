# 概要设计：前端透明化建设

- 日期：2026-09-28
- 来源需求：docs/requirements/需求.md（「前端透明化建设」）
- 状态：已定稿（3 轮 3 票质疑投票，第 3 轮 2/3 通过，详见 §12）

## 1. 背景与目标

为电信运营商业务办理系统建设前端透明化平台：基于原生 OpenTelemetry 采集前端业务流程数据，端到端链路为
**浏览器 SDK → OTLP/HTTP → 接收端（Spring Boot 3 + 内嵌 collector-embedded）→ Kafka → 存储端 → Databend → 查询端 → Vue 3 可视化**，实现业务办理流程可视（含后台 REST 接口调用情况）与性能指标（首屏加载、各业务耗时与成功率）。

业务系统形态：基座应用（Vue 2 + Module Federation 多模块）+ 子应用（统一货架、订单、产商品配置、已订购、购物车等，micro-app 接入，Vue 3）。

## 3. 总体架构

```
┌──────────────────────────── 电信运营商业务办理系统（浏览器） ───────────────────────────┐
│  基座应用 (Vue2 + Module Federation)          子应用 (Vue3 + micro-app)                │
│  统一货架 / 订单 / 产商品配置 / 已订购 / 购物车                                          │
│        └────────────── sdk-web（window 全局单例，vue2/vue3 双 adapter）────────┘        │
│        SigninManager · BusinessManager(挂起/恢复) · REST自动埋点 · 性能指标 · OTLP导出    │
└──────────────────────────────────────┬────────────────────────────────────────────────┘
                                       │ OTLP/HTTP 4318（仅 HTTP，gRPC out of scope）
                              ┌────────▼────────┐
                              │ receiver (SB3)  │  内嵌 collector-embedded 1.2.1
                              │ IP白名单/限流    │  只读 /config/producer、micrometer 指标
                              └────────┬────────┘
                     ┌─────────────────┼──────────────────┐
                     ▼                 ▼                  ▼
        nl-observe.otlp.traces   nl-observe.otlp.metrics  nl-observe.otlp.logs  (Kafka)
                     └─────────────────┼──────────────────┘
                              ┌────────▼────────┐
                              │ storage (SB3)   │  消费组 nl-observe-storage
                              │ OTLP解析→batch  │  写账号（最小权限）
                              └────────┬────────┘
                              ┌────────▼────────┐
                              │   Databend      │  otel_spans / otel_metrics / otel_logs
                              └────────┬────────┘  （ReplacingMergeTree，日分区，TTL 90d 假设）
                              ┌────────▼────────┐
                              │ query (SB3)     │  只读账号、参数化查询、审计日志
                              │ REST API        │  复用业务系统既有会话/网关鉴权
                              └────────┬────────┘
                              ┌────────▼────────┐
                              │ web-ui (Vue3)   │  业务列表 / 办理流程时间线 / 性能指标卡片
                              └─────────────────┘
```

组件职责：

- **sdk-web**：基于 @opentelemetry/sdk-web 的薄封装。SigninManager（一次一个客户，互斥）；BusinessManager（每业务一个独立 root span → 天然不同 traceId；挂起=记录 span event 不结束 span，恢复=继续；end 时写 `biz.total_suspended_ms`、`biz.effective_duration_ms`）；fetch/XHR 自动埋点（attribute 白名单）；性能指标只报原始 data point（不做统计聚合）；`pagehide`/`visibilitychange=hidden` 触发 sendBeacon best-effort flush。
- **receiver**：Spring Boot 3 进程内嵌入 collector-embedded 1.2.1 作 OTLP 接收器；仅 HTTP 4318（gRPC 4317 显式 out of scope，避免双入口与依赖风险）；Kafka exporter 参数与需求 yaml 一一对应；IP 白名单 + max 请求大小 + 限流；只读 producer 配置端点与丢弃计数指标（可测性）。
- **storage**：三个 consumer 解析 OTLP/JSON 载荷，JDBC batch 写 Databend 三表；at-least-once，ReplacingMergeTree + 查询端 FINAL 去重；连接串固定 `presigned_url_disabled=true`，启动时连接自检。
- **query**：连 Databend（只读最小权限账号）提供 REST API；全部参数化查询；审计日志；经业务系统既有网关鉴权。
- **web-ui**：Vue3 + Vite + TS；访问与 API 同经既有网关（外部边界依赖，不新建鉴权体系）。

**关键语义决策**

1. 业务耗时 = 有效耗时 = 墙钟 - Σ挂起时长（质疑者 1 第 1 轮意见）；span 墙钟时长保留 OTel 原义，展示与统计一律用 `biz.effective_duration_ms`。
2. SDK 不做任何跨会话统计聚合（无 P95/均值）——百分位不可合并（质疑者 1 第 1 轮意见）；SDK 只报原始 data point，P95/成功率由 Databend `quantile(0.95)`、sum/count 计算。
3. 范围澄清：SDK 仅上报 traces/metrics；logs 链路（/v1/logs + logs topic + otel_logs 表）是接收端/存储端通用能力（需求 yaml 含 logs topic），为业务系统日志预留，SDK 不主动发 logs；gRPC 4317 out of scope。
4. 模块边界：`backend-observe-common` 承载 DDL 常量/DTO/OTLP payload 模型/版本，receiver/storage/query 单向依赖 common、彼此不互依（质疑者 1 第 1 轮意见）。
5. 查询 API 均带 `customerId` 命中排序键前缀；`/metrics/summary` 的 `customerId` 可选：指定=客户作用域；不指定=显式声明的跨客户运维视图（日期分区裁剪 + 接口限流）（质疑者 1 第 2 轮意见）。

## 4. 仓库与模块划分

单仓库（本仓库 nl-observe）多模块，理由：三后端共享 DDL/DTO/OTLP 模型与版本，独立进程独立部署。

```
nl-observe/
├── pom.xml                          # 父 POM（SB3、JDK17、依赖版本管理）
├── backend-observe-common/          # DDL常量/DTO/OTLP payload 模型/统一响应/错误码
├── backend-observe-receiver/        # OTLP 接收 → Kafka
├── backend-observe-storage/         # Kafka → Databend
├── backend-observe-query/           # Databend → REST
├── sdk-web/                         # 前端 SDK（npm 包，core + vue2/vue3 adapter，双构建）
├── web-ui/                          # Vue3 + Vite + TS 可视化
├── tests/api/                       # Newman 集合
└── tests/e2e/                       # Playwright 用例（env-gated）
```

## 5. 接口清单

### 5.1 SDK 对外 API（sdk-web）

```ts
init({ serviceName, endpoint, exportTimeoutMs? = 2000, restPathFilter? })
sign_in(customerId): void            // 互斥：重复签入先隐式 sign_out
sign_out(): void
startBusiness(bizCode, meta?): bizId // 自动挂起其他 active 业务
suspendBusiness(bizId?): void
resumeBusiness(bizId): void
endBusiness(bizId, { status: 'success' | 'fail', endReason? }): void
trackRest(method, route, statusCode, durationMs): void   // 沙箱无法自动捕获时的手动兜底

// vue 指令（vue2/vue3 各一套注册，共享 core）
v-biz="'<bizCode>'"   // 组件 mounted 起业务 root span，unmounted 结束（未显式 end 计 fail，end_reason=unmount）
v-span="'<label>'"     // mounted 起子 span，unmounted 结束
```

- 单实例守卫：`window.__NL_OBSERVE__` 全局键 + 实例版本检查，防基座/子应用双初始化；micro-app jsSandbox 开启时 SDK 必须由基座提供。
- 会话中断：`pagehide`/`visibilitychange=hidden` 触发 sendBeacon best-effort flush；flush 失败/超时时尽力上报 `nl.sdk.flush` metric data point（attributes：flush=beacon、result=ok|fail|timeout、dropped_spans=N）。丢失容忍口径：在途数据可丢失，有计数。

### 5.2 接收端入口

- `POST http://<receiver>:4318/v1/traces`、`/v1/metrics`、`/v1/logs`（OTLP/HTTP protobuf；唯一入口，gRPC 4317 out of scope）
- 监听端口可配置（默认 4318，集成测试用随机端口）
- 安全：IP 白名单过滤器（业务系统网段）+ max 请求大小（超限 413）+ 限流（超限 429）

### 5.3 Kafka

| topic | 载荷 | key |
|---|---|---|
| nl-observe.otlp.traces | ExportTraceServiceRequest（OTLP/JSON） | nl.customer_id（确定性） |
| nl-observe.otlp.metrics | ExportMetricsServiceRequest（OTLP/JSON） | nl.customer_id |
| nl-observe.otlp.logs | ExportLogsServiceRequest（OTLP/JSON） | nl.customer_id |

producer 参数严格按需求 yaml：acks=all、idempotence=true、compression-type=lz4、linger-ms=5、batch-size=65536、delivery-timeout-ms=20000、request-timeout-ms=15000、retries=2147483647、max-in-flight=5、max-block-ms=5000、buffer-memory=67108864、send-timeout-ms=9000（< 库批次超时 10s）。

### 5.4 接收端运维端点

- `GET /config/producer` — 只读，返回生效 Kafka producer 参数（测试断言用）
- micrometer 指标：`nl.receiver.dropped`（丢弃计数，Kafka 故障注入断言用）、标准 http/kafka 指标

### 5.5 查询端 REST（/api/observe，统一响应 `{code, message, data}`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /customers/{customerId}/businesses?from&to&bizCode | 业务列表：bizId、bizCode、traceId、startTime、effectiveDurationMs、status、endReason |
| GET | /customers/{customerId}/traces/{traceId} | span 树（FINAL 查询；含 REST span 的白名单属性） |

## 6. 数据模型（Databend，草案）

三表均 **ReplacingMergeTree**（at-least-once 去重，去重身份 = ORDER BY 键），日分区，TTL 90 天（假设，待澄清）。凭证走环境变量，连接串含 `presigned_url_disabled=true`（地址见需求文档）。

```sql
-- spans：去重键 = 全 ORDER BY 键（同 span 重复上报折叠）
CREATE TABLE otel_spans (
  customer_id        String,
  trace_id           String,
  span_id            String,
  parent_span_id     String  DEFAULT '',
  trace_state        String  DEFAULT '',
  name               String,
  kind               UInt8,
  start_time         DateTime64(9),
  end_time           DateTime64(9),
  status_code        UInt8,
  status_message     String  DEFAULT '',
  biz_code           String  DEFAULT '',
  service_name       String,
  effective_duration_ms Float64 DEFAULT 0,
  resource_json      String,   -- JSON
  scope_json         String,   -- JSON
  attributes_json    String    -- JSON
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMMDD(start_time)
ORDER BY (customer_id, trace_id, span_id, start_time, end_time)
TTL start_time + INTERVAL 90 DAY;

-- metrics：dp_hash 使不同数据点互不折叠、同键重复折叠；查询前缀 (customer_id, metric_name) 命中排序键
CREATE TABLE otel_metrics (
  customer_id  String,
  metric_name  String,
  metric_type  UInt8,
  time         DateTime64(9),
  value        Float64,
  biz_code     String DEFAULT '',
  resource_json String,
  attributes_json String,
  dp_hash      String   -- hash(metric_name + time + resource_json + attributes_json)
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMMDD(time)
ORDER BY (customer_id, metric_name, time, dp_hash)
TTL time + INTERVAL 90 DAY;

-- logs：预留业务系统日志；行键折叠重复
CREATE TABLE otel_logs (
  customer_id     String,
  trace_id        String DEFAULT '',
  span_id         String DEFAULT '',
  time            DateTime64(9),
  severity_number UInt32,
  severity_text   String DEFAULT '',
  body            String,
  resource_json   String,
  attributes_json String,
  row_hash        String  -- hash(trace_id + span_id + time + body)
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMMDD(time)
ORDER BY (customer_id, trace_id, time, row_hash)
TTL time + INTERVAL 90 DAY;
```

查询端读 span 树/指标一律 `FINAL`；「写成功但 offset 提交失败」的残留重复窗口为记录在案的可接受风险。

## 7. Trace 上下文与属性约定

- 业务 root span：`name = biz.business.<bizCode>`，无 parent（每业务独立 → 不同 traceId）
- span events：`biz.suspend_start` / `biz.resume`；end 时属性 `biz.total_suspended_ms`、`biz.effective_duration_ms`、`biz.status`（success|fail）、`biz.end_reason`（explicit|unmount）
- REST span：`name = "HTTP {method}"`，属性白名单：`http.request.method`、`http.route`、`http.response.status_code`、`nl.duration_ms`；parent = 当前 active 业务 root span（无 active 业务时不产生 REST span）
- 客户标识：`nl.customer_id` = 业务系统客户编号（假名引用）；**禁止**手机号/证件号类属性进入 attributes（白名单约束 + 评审检查项）
- 指标 data point：`nl.first_screen_load`（ms，每页一次）、`nl.business_duration`（ms，每业务一次，attributes 含 biz_code/biz_status/end_reason）、`nl.sdk.flush`（flush 结果，best-effort）

## 8. 安全设计（质疑者 2 意见落实）

| 项 | 设计 |
|---|---|
| 查询/可视化访问控制 | 复用业务系统既有会话/网关鉴权（外部边界依赖，不新建鉴权体系；落地方式待澄清 #6） |
| 接收端入口 | IP 白名单（业务系统网段）+ max 请求大小 + 限流；gRPC 4317 关闭 |
| 数据防伪造/DoS | 上述入口控制 + 丢弃计数指标 |
| PII 控制 | SDK attribute 白名单（不自动上报 query/body）；客户编号假名化；接收端可配置附加脱敏映射（可选） |
| 注入防护 | 查询端全部参数化查询（JdbcTemplate named params，禁止字符串拼接） |
| 账号分离 | Databend 写账号（storage，仅三表写入）/ 只读账号（query）分离，最小权限 |
| 审计 | 查询端审计日志（时间/客户/traceId → 日志文件） |
| 凭证 | 全部环境变量；文档与代码库不落口令 |

## 9. 可靠性与性能

- Kafka 不可达：`max-block-ms=5000` 快速失败 → 丢弃并计 `nl.receiver.dropped`，进程不挂死（AC-10）
- Databend：连接串固定 `presigned_url_disabled=true`（本地盘/内置 MinIO 场景缺参会 "Failed to upload stream"）；启动连接自检；JDBC batch 写
- 存储去重：ReplacingMergeTree + FINAL（见 §6）
- 表增长：日分区 + TTL 90 天（假设）+ 指标只报原始点（量级可控）
- FINAL 大表查询性能：POC 验证（风险 #10），必要时按 customer_id 分区裁剪（API 已带 customerId）

## 13. 关键设计决策一览

1. 单仓库多模块（common 单向依赖）；三后端独立进程
2. 仅 OTLP/HTTP 4318 入口，gRPC 4317 out of scope
3. 每业务独立 root span（天然不同 traceId）；挂起不结束 span，有效耗时 = 墙钟 - Σ挂起
4. SDK 只报原始 data point，P95/成功率由 Databend 计算
5. Kafka 载荷 OTLP/JSON，key = nl.customer_id（确定性，可测）
6. 三表 ReplacingMergeTree + FINAL 去重；去重身份 = ORDER BY 键
7. 安全：复用既有网关鉴权 + IP 白名单 + attribute 白名单 + 参数化 + 账号分离 + 审计
8. 可测性内建：/config/producer、nl.receiver.dropped、端口可配置、确定性 key、env-gated E2E
